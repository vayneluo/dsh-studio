# DS Studio README and v0.1.2 Release Design

## Goal

Present DS Studio as a usable Windows desktop product, commit the approved brand assets to `main`, bump the desktop application to `0.1.2`, and publish the verified Windows x64 NSIS installer as the `v0.1.2` GitHub Release asset.

## Scope

This release contains exactly two product outcomes:

1. Replace the current implementation-first README opening with a product-first presentation of the desktop application.
2. Build the latest `main` code as version `0.1.2`, push the release source to `main`, and publish the installer through GitHub Releases.

It does not redesign the application UI, change the bundled plugin set, alter provider behavior, or add an updater.

## README Structure

The README uses a product-first hierarchy:

1. Centered `ui/brand.png` hero, product name, one-sentence positioning, version, platform, license, and a direct `v0.1.2` release link.
2. A concise product overview with `ui/logo.png` as the secondary brand visual.
3. User-facing capabilities: packaged Windows desktop experience, provider-neutral onboarding, OpenAI-compatible endpoints, bundled plugins, local process boundary, and preserved user data.
4. Supported model services, including domestic, international, local, and custom OpenAI-compatible options.
5. Installation and first-run instructions for the Windows x64 NSIS installer.
6. Privacy and data-storage boundaries.
7. Developer build, verification, runtime override, maintenance, and licensing sections.

GitHub-relative asset paths keep the README portable across branches and forks. HTML image tags may set display width and alignment, but the original PNG files remain unchanged.

## Brand Assets

- Commit the approved horizontal wordmark as `ui/brand.png`.
- Commit the approved square mark as `ui/logo.png`.
- Reference both files from `README.md`.
- Do not replace the existing Windows executable icon in this release; the requested scope is repository and README branding.

## Version Contract

The release version is `0.1.2` and the Git tag is `v0.1.2`.

Update every repository source that owns the application version:

- `src-tauri/tauri.conf.json`
- `src-tauri/Cargo.toml`
- the `dsh-studio` package entry in `src-tauri/Cargo.lock`
- version assertions in `scripts/runtime-policy.test.mjs`
- visible README version and download links

The expected installer name is `dsh-studio_0.1.2_x64-setup.exe`.

## Build and Verification

Before release:

1. Run the complete Node test suite.
2. Run the Rust test suite.
3. Run the ordinary and seeded HTTP smoke tests.
4. Build the NSIS installer from the release commit with `cargo tauri build`.
5. Run the installer audit and confirm the artifact remains within the repository's 70 MiB installer budget.
6. Calculate and record the installer's SHA-256 digest.
7. Confirm the worktree contains only the intentional source, documentation, and brand-asset changes before committing.

Tauri-generated schema line-ending changes are build artifacts and must not be committed when their content is unchanged.

## Git and GitHub Release Flow

1. Implement and verify on `codex/readme-v0.1.2-release`, based on the latest `main`.
2. Commit the README, assets, version sources, and version assertion.
3. Integrate the verified commit into local `main` without unrelated branch history.
4. Push `main` to `origin`.
5. Create tag and GitHub Release `v0.1.2` targeting the pushed release commit.
6. Upload only the NSIS installer as the release binary asset; do not commit the EXE into Git history.
7. Include product highlights, installer size, SHA-256, platform requirement, and the direct asset link in the release notes.
8. Re-fetch remote state and verify that `origin/main`, tag `v0.1.2`, the release target, and the uploaded asset all reference the intended release.

## Failure Handling

- Any test, smoke, build, installer audit, or hash failure stops the release before pushing or publishing.
- If `origin/main` advances, integrate and re-run verification before pushing.
- If tag `v0.1.2` or its release already exists, inspect it and stop rather than overwriting an unrelated publication.
- If GitHub Release upload fails after `main` is pushed, keep the verified local installer and report the incomplete release state; do not claim the release is complete.

## Acceptance Criteria

- `main` contains the product-first README and both approved PNG assets.
- All visible and source-owned versions read `0.1.2`.
- Node, Rust, ordinary smoke, and seeded smoke verification pass on the release source.
- `cargo tauri build` produces `dsh-studio_0.1.2_x64-setup.exe` within the 70 MiB budget.
- The SHA-256 digest is recorded in the GitHub Release notes.
- `origin/main` contains the release commit and the public `v0.1.2` Release exposes the installer for download.
